# 奇想校园｜商业版产品与设计规格 v1.0

设计日期：2026-10-16。状态：待业务负责人评审的产品设计基线，不是已实现功能声明。

配套：wonder-campus-preview.html 为可交互视觉原型，index.html 为独立预览包装。所有人物、校区、作品和经营数字均为虚构示例；原型不连接后端、不收费、不实际扣课。原型覆盖核心页面，设置等部分仅展示范围说明，不能作为完整功能验收。

## 1. 产品定义

一句话：让学校把时间还给教学，让家长看见成长，让每个孩子的好奇得到回应。

服务对象：六校区教育机构，英语、画画、语文、数学；学员3岁至高三；课时包和学期制并行；iOS优先，保留安卓路线。

商业版的核心价值：
- 教务：减少排课冲突、遗漏和手工对账。
- 老师：在明确的课堂上下文里签到、互动、记录、反馈。
- 家长：知道何时上课、学了什么、孩子有哪些具体变化、权益怎样使用。
- 负责人：六校区使用统一业务口径，能定位异常并追溯原单。

当前阶段首先服务自有六校区。商业化指可长期运营、交付与维护；是否向外部机构销售SaaS尚未决定。先预留运营组织/租户边界，不立即增加套餐计费、代理商和复杂多租户运营平台。

## 2. 当前界面为什么不成立

截图首页是开发验证入口：大品牌标题、技术实现说明、角色按钮、两个通用操作，以及大面积无内容空间。它没有回答今天有什么课、谁需要处理、孩子最近发生了什么。

改动原则：
1. 每个首页有一个主要任务，突出具体对象和时间。
2. 品牌在启动和登录表达；进入应用后让位于业务内容。
3. 角色切换位于“我的”；仅显示账号拥有的身份。原型外部切换器是评审工具，不能放进正式App首页。
4. “签到”从课次进入，“反馈”从课程和学员进入，避免无上下文操作。
5. 不展示运行框架、数据库字段、课次裸ID、DEMO、测试接口或“非原生”字样。
6. 空状态有原因、下一步和权限区分，不能只写“暂无”。

## 3. 信息架构

| 角色 | 一级导航 | 主要内容 |
|---|---|---|
| 家长 | 首页 / 课表 / 消息 / 我的 | 孩子切换、下一课、成长反馈、请假补课、权益、监护授权 |
| 老师 | 今天 / 课表 / 反馈 / 我的 | 课前准备、签到、班级名单、反馈草稿与发布、代课权限 |
| 教务 | 工作台 / 课表 / 学员 / 我的 | 排课、异常待办、请假审批、补课、报名合同、收费记录 |
| 负责人 | 概览 / 校区 / 经营 / 我的 | 六校区指标、异常、招生续费、收退费、课消、权限及审计 |

负责人可以获得教务身份，但不会默认具有所有校区、所有敏感字段的访问权。财务细节与儿童资料分别授权。

手机承担日常处理和现场工作。复杂学期批量排课、批量导入、财务对账和导出应保留桌面管理端路线，不能将表格缩小后塞进手机。

## 4. 视觉方向：有秩序的温暖

品牌名暂用奇想校园，英文辅助名WONDER CAMPUS；正式商标和名称可用性待确认。

主色为克制的鸢尾蓝，配柔和纸白背景与墨色正文；陶土橙用于少量重点内容，叶绿色表达已完成和正向状态。取消全屏橙色渐变和巨型按钮。

字体：iOS采用系统中文字体，避免依赖外部字体。页面主标题约28pt，区块标题19pt，正文16pt，辅助13pt，Tab标签11pt；全部支持Dynamic Type，不以固定高度裁切。原型为浏览器视觉样例，实际iOS字号需按平台缩放实现。

间距：4/8/12/16/20/24/32。页面边距20；主卡片圆角20—24；表单和按钮12；标签6—8。主操作最小触控区域44×44pt。优先文本与布局表达层级，不给每条列表增加卡片和阴影。

图标统一线性风格。品牌插画只出现在欢迎、探索主题和空状态，不能替代课程信息。作品内容是视觉主角；未授权作品不用于宣传。原型用几何作品示意，不冒充孩子真实作品。

动态：短暂状态反馈、轻量页面过渡；避免持续漂浮装饰与奖励动效。遵从减少动态设置。成功提示不依赖动画或颜色。

## 5. 核心页面设计

### P01 家长首页

顶部：孩子切换；同一账号只能看到经验证关联的孩子。问候语之后给年龄与课程概况。

第一屏：下一节课主卡，包含科目/主题、日期、时间、校区、教室、课程详情。无近期课程显示下一次安排待确认及联系教务入口。

常用入口：课表、请假补课、课程权益、成长档案。下方展示最近发布的具体反馈，而非打卡排行榜。

成长记录以具体观察为中心：“主动邀请同伴一起完成屋顶”。不生成创造力分数，不将学员之间的比较呈现给家长。

### T01 老师今天

顶部：校区及日期。简短工作量：今日课程、学员人数、待反馈；数字可进入对应列表。

主卡：下一课或进行中课程，主题、班级、人数、教室、请假提醒、进入课堂。已结束未处理课程显示待补记，不伪造实时课堂状态。

次级内容：课前探索问题、待发布反馈、代课及调课提醒。没有课程时提供查看未来安排和备课入口。

### O01 教务工作台

主内容是今日课程与待办，不以财务大屏占首页。待办分为请假、调课、补课、权益异常；显示数量、优先级和影响人数。

快捷任务：新增排课、报名、补课、登记收款。所有入口按权限显示。校区选择始终可见，跨校区操作需明确说明目标校区。

### B01 负责人概览

首要区分实际收款、退款、课消收入、未使用权益对应金额。指标标明范围、期间、更新时间与计算口径。指标进入明细，明细回到原单。

出勤率、在读人数、续费等必须定义分母、排除项和时间口径。不同币种不得直接相加。原型仅示意，未连接经营数据。

### C01 课表

手机默认日视图：周日期条+按时间排列的课程列表。周网格作为切换视图，不能强迫用户在窄屏拖动细格。

教务筛选校区、老师、教室；老师默认本人；家长默认当前孩子。课程时间重叠仍清楚展示，不靠颜色区分。状态：待上课、进行中、已完成、已取消；是否进行中按时钟与业务状态分开展示。

### C02 课程详情

课程主题、班级、时间地点、授课老师、材料准备、内容目标和考勤状态。家长看与孩子相关的信息；老师看名单与课前任务；教务看调整及审计。

操作只针对当前课次。调课必须选择“仅本次”或“本次及后续/整组”并预览受影响课次；存在已完成课程时禁止静默批量修改。

### T02 签到及纠错

名单按真实报名关系返回。批量设置只是编辑，确认后才提交。提交前展示每种状态人数及不同权益影响，不能统一宣称所有人都扣1课时。

并发更新：显示服务端最新版本并让老师重新确认，不覆盖他人修改。已提交再次进入显示记录和更正入口。更正保留原记录、冲正原因和权限，不删除历史。

### T03 反馈编辑、预览与发布

从课次和孩子进入。支持班级共同内容与每个孩子独立观察，两者在预览中组合。可保存草稿、切换学员、选择作品。保留草稿状态与未完成名单。

最小字段：今天探索、一个具体观察、下一步鼓励；老师可自由编辑，不强制填满所有字段。不得自动替所有孩子编造表现。

预览显示接收人、孩子、作品与可见范围。发布后提供版本及修改记录；内容修改不重复轰炸通知。幼儿照片涉及其他孩子时也要校验展示授权。

### P02 成长档案

按时间组织作品、表达、探索与反馈，支持科目筛选。记录属于具体孩子，不等于聊天动态。阶段总结引用真实观察与作品，不制造人格标签。

3—6岁：亲子查看、作品和口头表达；小学：探索与讲述；初高中：项目过程、学习方法、自主目标。高中页面保留成熟视觉，不使用幼儿勋章文案。首版不开放学生独立账号，后续再设计适龄授权。

### P03 课程权益

课时包：剩余付费/赠送数量、有效期、适用范围、流水。学期制：总安排、已完成、待上、取消与补课。两种权益分别展示，不相加成“总剩余课时”。

每条流水有业务时间、原因、关联课次、数量、余额及冲正关系。退款预估只是试算，需核算规则确认后才可执行。家长不应看到内部成本和其他学员合同。

### P04 请假补课

选择具体孩子与课次→显示该合同规则→选择原因/可选说明→确认→结果。避免收集详细疾病诊断。

审批后展示是否扣权益、补课资格及期限。资格与原课关联；已安排补课、已使用、取消请假要分别控制。不承诺所有已批准请假都自动产生补课，按合同判断。

### O02 排课

班级、校区、老师、教室、起止时间、重复规则。保存前检查老师/教室/学员冲突，并对并发保存做后端约束。失败列出冲突对象、课次和时间，不自动挪动其他课程。

批量重复排课先预览节假日、已有课程、无效日期和冲突；显示全部/部分成功策略，避免部分成功却只显示失败。

### O03 报名与收款

学员→课程班级→收费方案→优惠→合同及权益快照→确认报名。收款作为独立步骤，显示实际收款主体、方式、时间和原始单据。

支持欠款、分次收款、退费审批及记录，收据号由后端生成。未支付是否可上课取决于明确规则，不默认放行或全部禁止。首版人工登记收款，不显示虚假的在线支付完成。

### M01 消息

通知分类：课表、请假补课、课堂反馈、费用权益、系统。列表可进入对应业务；通知读状态不改变业务审批状态。多孩子信息明确标识。

首版是可追踪的应用内通知，不承诺即时通讯或系统推送。APNs等单独实现与验证。发送失败不回滚已完成签到，但进入重试队列。

### A01 我的与隐私

身份与授权、孩子及监护关系、校区、通知设置、隐私作品授权、帮助、关于、退出。监护人邀请必须验证身份与关系，不能通过搜索姓名直接认领孩子。

作品可见范围分为教学记录、班级分享、机构宣传，不能一次勾选捆绑授权。撤回授权后阻止后续使用，并说明历史已发布材料的处理路径。账户删除、资料保留和法定凭证保留规则在正式发布前确认。

## 6. 核心流程与业务边界

1. 报名：合同版本→权益账户→收款记录。合同生效、收费和权益可用分别有状态，不能用一个paid布尔值替代。
2. 教学：课次→考勤→权益流水→完成课次。签到、消课与课消收入确认按规则处理，不因打开页面自动发生。
3. 请假：申请→审批→权益处理→补课资格→补课课次→资格核销。每一步保留关联和审计。
4. 课程取消：检查已签到/补课/财务后果→展示影响→事务执行→通知，不仅修改日历显示。
5. 反馈：草稿→预览接收范围→发布→受控修改。媒体对象与元数据均需权限控制。
6. 跨校区：权益授权与老师排课权限独立，跨校区使用有来源记录，收款主体和课消归属不得隐式改变。

事务约束：幂等键绑定请求体；同一业务只产生一次有效扣课；考勤更正通过反向流水；补课资格唯一核销；库存式余额字段不能成为唯一事实来源；并发排课/退款/扣课做数据库级校验。所有关键写入记录操作者、组织、校区、时间、原因和前后版本。

## 7. 组件与状态交付要求

组件：AppShell、RoleContext、CampusPicker、ChildPicker、CourseCard、DayStrip、AttendanceRow、EntitlementSummary、LedgerRow、FeedbackComposer、MediaGrid、ReviewSheet、MoneyField、ErrorBanner、EmptyState、Skeleton、ConfirmationSheet。

每个页面必须交付：正常、加载、无内容、无权限、网络失败、登录过期；表单另有验证失败、保存中、版本冲突和未保存离开。不得用空数组掩盖错误。

可访问性：大字体不裁切、VoiceOver名称与状态、逻辑阅读顺序、非颜色状态提示、44pt触控区、减少动态。检查深色模式、键盘、长名字、多校区、弱网与重新登录。

内容语气：具体、友好、不评判。示例：“这节课已提交7位学员的出勤记录”；“保存失败，内容仍保留，请重试”；“当前账号没有查看这份记录的权限”。避免“操作成功”无上下文和“宝宝不乖”等评判。

## 8. 技术落地与商业运营

JNative继续承担业务服务。iOS原生界面与现有WebView方案的选择应通过当前工程评估，不把原型当作框架承诺。若现有壳能稳定交付，可先依本规格重做；若选择SwiftUI，应作为独立范围迁移，复用后端，不能一边换栈一边改全部业务。

商业运营的必备设计范围：
- 独立应用身份，开发/测试/正式配置；测试数据与入口不进入正式构建。
- 身份验证、权限、敏感字段和媒体访问控制；服务端按组织与关联验证。
- 数据库迁移、备份恢复、审计、附件清理、监控、错误追踪及用户支持。
- 账号邀请/离职停用/监护关系变更；授权撤销后缓存清理。
- 多设备会话、登录失效、时间与金额口径、数据导入导出及恢复演练。
- 发布前核实适用地区的教育业务、收费、儿童信息、隐私、商店审核要求；本设计不是法律合规结论，须按实际经营地区和主体确认。

商业版不是把所有功能一次堆满。第一阶段完整交付排课—上课—反馈—权益—收款查询与必要异常；第二阶段批量运营、退费复核和报表；第三阶段在实际使用基础上加入招生、内容库和辅助工具。AI与学生社区不进入首发必备范围。

## 9. 发布验收门槛

| 维度 | 可签字标准 |
|---|---|
| 视觉 | 关键页面按设计逐页核对，小屏/大屏/大字体/深色无截断、遮挡和占位文案 |
| 业务 | 两种收费方式各完成报名、收款、排课、请假、补课、签到、更正、取消与回查 |
| 隔离 | 家长、代课老师、教务跨孩子/班级/校区/组织负例均拒绝；媒体同样验证 |
| 一致性 | 并发/重复请求不重复扣课退款；失败完整回滚；余额与流水及财务明细一致 |
| 手机 | iOS模拟器及至少一台真机完整验收，前后台切换、断网重连和重启通过 |
| 运营 | 恢复演练、错误定位、审计、支持入口和账号停用可用 |
| 产品 | 教务、老师、家长各至少两位代表完成任务测试，记录阻塞和误操作，修复后复测 |

内部体验目标（待试点校准，不是现成事实）：老师为8人完成正常签到在30秒左右；教务1分钟内完成无冲突的单次排课；家长10秒内找到下一课与请假入口。以观察与计时验证，不能靠设计人员自评。

## 10. 待确认事项与当前假设

- 六校区运营与收款主体关系：模型分开，具体配置待确认。
- 学期制缺勤、请假、补课、退款与收入分摊：由负责人确认并形成合同快照，原型规则只是示例。
- 是否有一对一、走班、跨科目通用权益、直播课：不默认纳入首版。
- 教师薪酬、招生顾问、支付网关、学生独立账号：后续范围。
- 品牌名称、真实校区名称、课程体系与素材：评审后替换，不使用虚构数据上线。

## 11. Cursor实施约束

先读本规格并盘点当前工程。保留已通过业务服务与验收，不另造账务和扣课逻辑。建立设计变量与组件，再按家长首页、老师今天、课表、课程详情、签到、反馈、权益、请假、教务待办顺序交付。

每次交付一条真实链路及实际运行截图；演示数据与连接真实服务状态明确区分。不能仅套颜色、改圆角或把原型复制为无业务按钮。不得把尚未完成的设置页、报表、上传和通知宣称已实现。

首轮只验收四种角色首页、课程详情和签到/反馈链路的视觉与操作一致性。之后继续报名、收退费与批量排课。未确认的业务规则集中提问，其余独立工作继续。
